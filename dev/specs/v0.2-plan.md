# v0.2 plan: a neutral install, issues as the human's queue, judgment over caps

Status: approved by Eric 2026-10-07 with all defaults (merge PR #1 first, `.agents/`, one issue per feature).
Built on branch `v0.2`; item 6 (Raze 2 migration) waits for a separate go-ahead.

## Why
Raze 2 (`~/code/personal-projects/raze-2`) is the first real project to use the kit. It showed three problems:
1. **The install takes over the repo.** It was 134 files and 4,498 lines, and only ~8 of the files were Raze 2's
   specs. The rest was the kit's examples (41), both profiles (13), and the kit's own scripts, tests, docs and
   branding (33). That included Eric's `docs/story.md`, the kit's CHANGELOG/CONTRIBUTING, and "agent-brigade" in
   18 files. The cause is v0.1's design: copy the whole kit, then run init inside it.
2. **What needs the human is scattered.** It lives in inbox files, "open an issue" instructions nothing carries
   out, and a status file. Nothing reaches the human; they have to go looking.
3. **A hard rule where judgment belongs.** The 400-line PR cap forced artificial splits (Raze 2 raised it to 1,000).
   The real ShellHacks failure was an untested feature merged right before the deadline, and the freeze already
   blocks that.

## Decision criteria (in order)
1. The project looks like the project. An install adds a small, neutral scaffold with no kit branding.
2. One place for the human: GitHub Issues.
3. Hard rules only where they protect something: a green `main`, ownership, the freeze, no secrets, no invented
   data. Everything else is guidance an agent applies like a good engineer.
4. Keep the loop that works. This is cleanup and centralizing, not a redesign.

## Checklist

### 1. Install from outside, into the project
- New flow, which also works on an existing repo like Raze 2:
  ```bash
  git clone https://github.com/Eric-Zhang-Developer/agent-brigade ~/somewhere/agent-brigade   # once
  python3 ~/somewhere/agent-brigade/install.py --profile project --lite [TARGET_DIR]           # default: .
  ```
  The kit stays in its own repo. The project receives only what it runs.
- **Installed layout (about 20 files):**
  ```
  AGENTS.md                 the rules AND the loop (~1 page, neutral), plus a short section for the profile
  CLAUDE.md                 @AGENTS.md
  .agents/config.toml       was kit.toml
  .agents/scripts/          lib, check_ownership, check_markers, check_gates, status, sync_issues, watchdog
                            (+ verify_release, demo_snapshot for hackathon)
  .agents/hooks/pre-commit
  specs/mission.md tech-stack.md roadmap.md features/_template/spec.md decisions/_template.md
  specs/gates.toml (hackathon) | specs/milestones.toml + NOW.md (project)
  changes/                  done notes (unchanged)
  .github/workflows/ci.yml  .github/pull_request_template.md  .github/ISSUE_TEMPLATE/needs-human.md
  ```
- **No fingerprint:** no installed file contains "agent-brigade", the kit's docs, examples, the story, or a second
  profile. A test installs into a temp repo and asserts that.
- **Upgrading:** re-running `install.py` refreshes `.agents/scripts` and `.agents/hooks` (owned by the kit), adds
  any missing files, and never touches `AGENTS.md`, `specs/` or `NOW.md` once they exist. `--profile`/`--lite`/
  `--full` switch modes the same way as v0.1.
- Human-facing guides (preflight, plan bake-off, judge agent, pitch, weekly routine, planner and briefing prompts)
  stay in the kit repo. The human reads them there, and nothing in the project points at them.

### 2. GitHub Issues as the human's queue
Specs stay files: they're what agents build from, versioned with the code. Issues are a **view onto them**, never a
copy.
- **`sync_issues.py`** (runs in CI on every push to `main`): one issue per feature spec, titled `[F07] name`, with
  a body that's a link to the spec plus one line, labelled `feature`. It closes the issue when `changes/F07.md`
  lands. It's idempotent: it matches issues by title prefix and never edits a human's comments.
- **Judgment calls → `needs-human` issues** (plus `one-way-door` where it applies), filed by agents with
  `gh issue create`. This **replaces `specs/inbox/`**. One-way doors still get no default.
- **Problems → issues:** `main-red` (the watchdog files and closes it automatically), `blocked`,
  `contract-change`.
- **Status → one pinned issue** whose body `status.py --issue` rewrites. This replaces committing
  `reports/status.md`, which spammed the history at ShellHacks. `--out FILE` stays for offline use.
- `install.py` creates the labels (`gh label create --force`). Without `gh`, everything prints instead and says so.
- **The human's checkpoint:** open Issues → filter `needs-human` → read the pinned status → merge or trim the
  `[PLAN]` PR.

### 3. Judgment over caps
- **PR size becomes a warning:** CI prints a non-blocking annotation past `[pr].warn_lines` (default 400) and asks
  for a split along logical seams or a one-line reason in the PR. The hard cap goes away.
- **The freeze stays hard.** No new feature PRs after the freeze. A big `[FIX-]` during the freeze gets the
  warning too.
- `AGENTS.md` separates **Must** (enforced by a check) from **Prefer** (engineering judgment), so it's clear which
  rules are walls.

### 4. Fixes
- Upstream Raze 2's `724b4b3`: the staged/base marker scans skip binary files (drop `--text`), with its test.
- **Worktrees outside the projects folder:** the default becomes `~/.worktrees/<repo>/<id>`, configurable in
  `.agents/config.toml`. This stops `raze-2-f13`-style siblings from appearing in `~/code/personal-projects/`.

### 5. Kit repo updates
- README and quickstart describe the new install flow.
- The examples are reshaped to the installed layout. Their loop-replay tests stay.
- CHANGELOG v0.2.0.

### 6. Raze 2 migration (separate step, after v0.2 is green)
Remove the kit leftovers, run `install.py` over it, keep its specs and `NOW.md`, and turn any inbox items into
issues. It touches another repo with active worktrees (`raze-2-f13`, `raze-2-f14`), so it needs Eric's go-ahead
and finished or parked worktrees first.

## Not doing
- Feature specs living in issue bodies. Specs stay files; issues link to them.
- A GitHub Projects board (it's easy to add later on top of labelled issues).
- Any change to the loop itself: claims, ownership, done notes and decisions stay as they are.
