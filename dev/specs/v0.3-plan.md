# v0.3 plan: names people can read, one deadline model, a lighter loop

Status: approved by Eric 2026-10-07 with all defaults, with a go-ahead for items 0–9 start to finish. Built on
branch `v0.3` from `main` (v0.2 merged as #2). Item 10 (Raze 2) stays parked.

## Why
Raze 2's merged PRs (37 merged, 0 reverts, main green on its last 38 runs) show that the core loop works. What
gets in the way is everything around it:
1. **IDs are lookups, not names.** `[FIX-F14] Bot difficulty` is readable only because the title repeats the name.
   The folder already says `F14-bots`. The number adds nothing, and on a long-lived app one flat counter grows into
   noise (F16 after a few days).
2. **Process PRs are a quarter of the PRs.** 7 contract and 3 plan PRs make 10 of 37 (27%). C4–C6 fought the line
   cap (v0.2 already fixed that), and C7 relaxed "one feature at a time". One title was a status update disguised as
   a fix (`#47 [FIX-F14] NOW.md: minimum playable reached`) because no title kind allowed it.
3. **Draft-PR claims did nothing in a solo run.** PRs stayed open for 4 minutes on average: one agent opened the
   PR right before merging it. Claims only matter when agents work in parallel.
4. **Six ideas do two jobs.** `phase`, stages, gates (`only`, `no_new_phase`, `freeze`, `report`, `hard_stop`),
   milestones, `cut: ok|never` and cut lists all answer just two questions: what ships in which release, and when
   the doors close. The hackathon and project profiles answer them in two different files.
5. **There's no version stamp.** v0.2 removed the fingerprint and the version went with it, so an upgrade can't
   tell which migration applies.
6. **Nothing measures the loop.** The numbers above were computed by hand.
7. **Done notes are never rolled up.** "Nobody understood the code" (ShellHacks) is only half-fixed: each feature
   has a note, and no page per release reads them together.

## Decision criteria (in order)
1. **Both profiles, one model.** A hackathon is a project with a short clock. Profiles differ in times and
   defaults, not in concepts.
2. **Readable to a person first, unique to a script second.** Use what engineers already know (Conventional
   Commits, GitHub Milestones, releases) before inventing a convention.
3. **Hard rules only where they protect something** (v0.2's rule, unchanged).
4. **The loop stays.** Specs, ownership, done notes, decisions and self-merge on green don't change.

### 1. The slug is the ID
- The feature's folder name is its ID: `specs/features/bots/spec.md`, `changes/bots.md`, branch `bots`, worktree
  `~/.worktrees/<repo>/bots`. The filesystem guarantees uniqueness, and it works offline (unlike issue numbers).
- Slug rule: lowercase-kebab, at most 32 characters. Reserved: `_template`, `shipped`, `contract`, `plan`, `docs`,
  `revert`. The spec linter enforces it.
- `id` leaves the front matter. Decisions are named `specs/decisions/<slug>-<topic>.md`.
- Order no longer comes from numbers. It comes from the milestone's `features` list (item 3).

### 2. PR titles use Conventional Commits
| Title | May change |
|---|---|
| `feat(<slug>): …` | the feature's `owns`, its spec, done note and decisions; the feature must not be done yet |
| `fix(<slug>): …` (also `refactor`, `perf`, `test`, `chore`) | the same paths, for an in-flight or shipped feature |
| `fix: …` without a scope (same types) | any path that isn't frozen and isn't owned by an in-flight feature |
| `docs: …` | `open` paths, plus Markdown outside `specs/` and frozen paths (`NOW.md` updates go here) |
| `contract: …` | frozen paths and `specs/` (additive, as today) |
| `plan: …` | `specs/features/`, `specs/milestones.toml`, `specs/roadmap.md`; a person merges it |
| `revert: …` | exactly what the reverted commit changed (`git revert` writes this title) |

- A `bootstrap: true` feature (and its fixes) may still change anything.
- `parse_title` returns `{kind, scope, type}`, and `check_ownership.allowed` keys on `kind`. The rule logic barely
  changes.
- The scope-less `fix:` row is what makes a mature app workable: a bug in shared code doesn't need a spec, and
  ownership still protects work in flight.

### 3. Milestones replace gates, phases and stages, in both profiles
One file, `specs/milestones.toml`. `gates.toml` is deleted.
```toml
start = ""                      # hackathon: launch time with UTC offset; enables "+H:MM" below. Empty = off.

[[milestone]]
name = "core"
ship = "+20:00"                 # project: "2026-11-15"; hackathon: an offset from start, or an absolute time
freeze = "2:00"                 # project: "2d". Inside the window, only this milestone's features and fixes merge.
features = ["map-data", "bots"] # in priority order: agents take the first ready one
cut = ["bots"]                  # rejected once the freeze starts

[[milestone]]
name = "submission"
ship = "+35:30"
freeze = "5:30"
final = true                    # the reporter's window starts report_before ship; at ship, nothing merges
report_before = "1:30"
allow = []                      # e.g. the reporter's feature, allowed during freeze and report
```
- **Bootstrap first is built in.** No other `feat` merges until the bootstrap feature's done note exists. That
  replaces the `only = ["F00"]` gate.
- **The current milestone** is the earliest one whose `ship` hasn't passed. Agents only pick features from it.
  Specs in no milestone are the **backlog**: listed in status, never picked.
- **Dropped:**
  - `phase` and `no_new_phase`: a feature that shouldn't start late goes in a later milestone or on a cut list.
  - Stages R0–R3 as a concept: the hackathon template ships them as three named milestones.
  - `cut: ok|never` in front matter: the cut list is the only place cuts are decided.
- **Front matter:**
  ```yaml
  ---
  name: Bots
  depends_on: [match-hud]
  owns: [native/src/ai/, native/tests/ai]
  assignee: ""          # replaces lane + agent; empty = anyone
  bootstrap: false
  ---
  ```
  The milestone isn't in front matter. `milestones.toml` is the one place that says what ships when, and in what
  order. (This refines the earlier sketch, which put the milestone in the spec: two places would drift.)
- The linter checks that every slug in `milestones.toml` exists and appears in at most one milestone, and that
  `depends_on` names real slugs.

### 4. Issues and GitHub Milestones
- An issue's title is the spec's `name`. `sync_issues` matches issues by a hidden `<!-- spec: bots -->` line in the
  body, not by title, so people can retitle issues freely.
- `sync_issues` creates a **GitHub Milestone** for each `[[milestone]]` (with a due date when `ship` is a date or
  can be resolved from `start`) and assigns each feature issue to it. This gives a progress bar per release for
  free. The `issues: write` permission already covers milestones.
- A release is `gh release create <milestone> --generate-notes`. GitHub lists the merged PR titles, which read
  cleanly as Conventional Commits.

### 5. A lighter loop at lite size
- **Lite:** no draft-first claim. Open the PR when the work is ready. The watchdog's stale-claim checks run only
  at full size.
- **Full:** the draft PR stays the claim.
- "One feature at a time" becomes a Prefer rule. `[agents].max_in_flight` (default 1 for lite, 2 for full) is
  what status warns about; nothing blocks on it.

### 6. Version stamp
- `.agents/config.toml` gets `schema = 3`: neutral, with no kit name.
- `install.py` reads it on re-install:
  - a missing stamp means v0.1/v0.2
  - an older stamp makes the installer print the matching section of `docs/upgrading.md` and stop, unless you
    pass `--upgrade`
- Upgrading only refreshes kit-owned files. It never rewrites specs.

### 7. Loop health in status
`status.py` adds a "Loop" section, from `gh` (online) or squash-merge subjects (offline, counts only):
- merged PRs by type, and the overhead share (contract + plan + docs out of the total)
- median minutes a PR stays open
- fixes per feature (the top 3)
- reverts
- minutes `main` spent red in the window (from `gh run list`)

### 8. A ship step and readable done notes
- **Done notes get fixed headings:** *What shipped*, *Where it lives* (paths), *How to check it*, *Gaps*. Still
  3–8 lines of content.
- **`.agents/scripts/ship.py <milestone>`:**
  - moves the milestone's done specs to `specs/shipped/<milestone>/`
  - writes `specs/shipped/<milestone>/README.md`, one walkthrough per release, stitched mechanically from the done
    notes and decisions (no model call, so it's only as good as the notes)
  - prints the `gh release create` command

  The human runs it, or it goes in a `plan:` PR.
- **Shipped specs still count for `fix(<slug>)` scopes.** The `owns` overlap check applies only among in-flight
  specs, so a new feature can extend code that a shipped one owned. That's the change that keeps ownership
  workable as an app matures.

## Results (2026-10-07)
- **Item 0 found four defects in v0.2**, all fixed here:
  1. The hook wrote `.agents/scripts/__pycache__`. `git add -A` committed it, and the ownership check failed.
  2. The merge step didn't wait for CI. `gh pr merge` merged a red PR on a repo without branch protection.
  3. The Status issue listed its own in-progress run as `main` CI.
  4. The actions ran on deprecated Node 20.

  Labels, the feature issue, the pinned Status issue and issue closing all worked live, and so did making `ci` a
  required check.
- **Verified live on `agent-brigade-smoke`, after upgrading it from schema 2 by following `docs/upgrading.md`:**
  - the installer stops on schema 2
  - the GitHub milestone is created with its due date and stays unchanged on the next sync (GitHub stores the date
    at midnight UTC, so the sync compares dates only)
  - the feature issue is filed on its milestone and closed by the merge
  - the Loop section reports the stats
  - `gh pr checks --watch && gh pr merge` refused a scope-less `fix:` that edited `AGENTS.md`

  The upgrade surfaced one more doc step: the installer never rewrites `ci.yml`, so the doc now says to bump the
  actions by hand.
- **Deviations from the checklist:**
  - `[agents].max_in_flight` wasn't added. The Prefer rule ("one feature at a time; a second while the first waits
    on CI") covers it, and status already lists every open PR.
  - The milestone lives only in `milestones.toml`, not in front matter, as noted in item 3.
  - The install cap in the tests went from 24 to 25 files for `ship.py`.
- Tests: 100 kit tests plus both examples' suites pass locally on Python 3.11.4 and 3.14.8.
