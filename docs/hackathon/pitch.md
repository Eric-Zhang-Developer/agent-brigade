# Pitch: 3 minutes, then questions

At ShellHacks, the product had too many features to demo in the slot; showing everything would have taken 5–10
minutes. The 45-second core visual loop is what won the room. Plan the pitch around that loop.

## Budget
| Time | Part |
|---|---|
| 0:00–0:30 | **The problem**, with one concrete example and why it costs someone money or time. |
| 0:30–1:15 | **The core loop, live** (about 45 seconds). One path, no detours. |
| 1:15–2:15 | **How it works**, in three sentences, then the one technical thing you're proudest of. |
| 2:15–2:45 | **Honest numbers:** what's real, what's verified, and what isn't done yet. |
| 2:45–3:00 | **What's next**, and the ask. |
| Then | Questions: about 2 minutes. Use `judge-agent.md`'s five hardest questions as practice. |

## Rules
- **One money shot.** If the core loop doesn't make the point on its own, fix the loop, not the script.
- **Say your limits out loud.** "Only 46 of 3,287 locations are independently confirmed" made every other number
  believable.
- **Talk to the sponsor early.** Demo to them mid-event, write their feedback into `specs/context/`, and come back
  with it built in. They'll recognize their own words.
- **Everyone can explain it.** Each teammate can answer "how does your part work?" (`docs/briefing.md`).
- **Have the fallback ready** (`demo-snapshot.md`) and a recorded video of the loop.
- **Submit early.** Write the submission text from `docs/briefing.md` and the Status issue before the freeze, not
  after.

## Template
```
Problem:       ___ (who) can't ___ (do what), which costs ___ (cite the source).
Core loop:     1. ___  2. ___  3. ___  → the moment the user sees ___.
How it works:  ___ → ___ → ___.  Proudest technical piece: ___.
Honest:        Real: ___. Verified: ___. Not done: ___.
Next / ask:    ___
```
